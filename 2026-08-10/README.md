# 2026-08-10｜数据库事务模板练习

## 当天练习

今天使用 `MockDB` 和 `MockTx` 模拟数据库事务，实现了一个通用的 `execTx` 事务模板，并通过转账业务分别练习事务成功提交和发生错误后回滚。

**和什么有关：** Go 高阶函数、回调函数、数据库事务、错误处理、`context.Context`，以及 Store 数据访问层。

## 小项目结构

```text
2026-08-10/
├── main.go    # 模拟事务、事务模板、转账业务和运行入口
└── README.md  # 当天练习总结
```

`main.go` 中的主要结构：

- `MockDB`：模拟数据库连接，通过 `BeginTx` 开启事务。
- `MockTx`：模拟事务对象，提供 `Commit` 和 `Rollback`。
- `Store`：保存数据库连接，负责执行数据访问逻辑。
- `execTx`：统一控制“开启事务、执行操作、提交或回滚”。
- `TransferTx`：模拟需要事务保护的转账业务。
- `TransferParams`：保存转账金额和是否模拟失败。

## 快速复习

事务执行流程：

```text
BeginTx
   ↓
执行 fn(tx)
   ├── 成功 → Commit
   └── 失败 → Rollback → 返回原始错误
```

`execTx` 接收一个函数参数：

```go
fn func(tx *MockTx) error
```

业务代码只需要描述“事务里面做什么”，提交和回滚由 `execTx` 统一处理。可以把它理解为：业务人员负责处理订单，事务模板负责最后盖章或撤销。

## 怎么运行

从仓库根目录执行：

```powershell
go run ./2026-08-10
```

程序会依次演示：

1. 正常流程：开启事务 → 执行业务 → 提交事务。
2. 异常流程：开启事务 → 返回错误 → 回滚事务。

## 常见问题

- 为什么不能在业务函数中随处调用 `Commit`？统一放在 `execTx` 中，才能保证所有业务使用相同的提交和回滚规则。
- 为什么回滚错误也要处理？如果业务执行失败并且回滚也失败，需要同时保留两个错误，方便排查数据库状态。
- `context.Context` 有什么用？真实数据库中可以传递取消和超时信号，避免事务无限等待。
- `BeginTx` 成功后，每一条属于该事务的 SQL 都应该通过 `tx` 执行，不能绕过事务直接使用 `db`。
- 当前代码是模拟事务，没有连接真实数据库，也没有真正转移金额。
